# Ответы на контрольные вопросы

## Практическое занятие № 1

## 1. Чем отличается Git от GitHub?
Git — это распределённая система контроля версий (консольная утилита), которая работает локально на компьютере и отслеживает историю изменений файлов.
GitHub — это облачная платформа (веб-сервис) для хранения Git-репозиториев и организации совместной работы над проектами. Git можно использовать без GitHub, но GitHub не работает без Git.

## 2. Для чего используется виртуальное окружение Python?
Виртуальное окружение (venv) используется для изоляции зависимостей конкретного проекта. Это позволяет разным проектам на одном компьютере использовать разные версии одних и тех же библиотек, не конфликтуя друг с другом. Оно также упрощает перенос проекта на другой компьютер, так как все зависимости фиксируются в requirements.txt.

## 3. Что такое commit, branch, remote, pull request?
- Commit — фиксация (сохранение) изменений в истории проекта с уникальным хешем и сообщением.
- Branch — отдельная независимая линия разработки, позволяющая вносить изменения, не затрагивая основную стабильную версию кода.
- Remote — версия репозитория, размещённая на удалённом сервере (например, на GitHub), с которой синхронизируются локальные изменения.
- Pull Request — запрос на слияние изменений из одной ветки в другую. Используется для код-ревью и обсуждения изменений перед их добавлением в основную ветку.

## 4. Зачем нужен файл .gitignore?
Файл .gitignore определяет список файлов и папок, которые Git должен игнорировать и не добавлять в репозиторий. Это необходимо, чтобы не засорять репозиторий временными файлами (например, __pycache__), локальными настройками (.vscode/), виртуальным окружением (.venv/), а также конфиденциальными данными (.env) или большими наборами данных (*.csv, *.xlsx).

## 5. Как организовать командную работу над бизнес-приложением с помощью Git?
Для этого используется ветвление (branching) и Pull Requests:
1. Основная стабильная ветка — main.
2. Каждый разработчик создаёт отдельную ветку под свою задачу (например, feature/add-kpi-calculation).
3. Работа ведётся в своей ветке, изменения коммитятся и отправляются на GitHub (`push`).
4. Создаётся Pull Request в ветку main, назначается ревьюер.
5. После проверки и исправлений изменения сливаются (merge) в main.
6. Все разработчики регулярно делают git pull origin main, чтобы получать актуальные изменения.

## 6. Какие файлы обязательно должны быть в репозитории учебного проекта?
- README.md (описание проекта, инструкция по запуску).
- .gitignore (список игнорируемых файлов).
- requirements.txt (список зависимостей).
- Исходный код (например, main.py).
- Папка docs/ с проектной документацией (бизнес-требования, ответы на вопросы и т.д.).

## 7. Что произойдёт, если два разработчика изменят один и тот же файл в разных ветках?
При попытке слияния этих веток (merge) возникнет конфликт слияния (merge conflict). Git не сможет автоматически определить, какие изменения оставить. Разработчику, выполняющему слияние, придётся вручную открыть файл, выбрать нужный вариант кода (или объединить оба), удалить маркеры конфликта, сохранить файл, добавить его в индекс (git add) и завершить слияние коммитом (git commit).

## Практическое занятие № 2

### 1. Чем отличаются бизнес-требования от функциональных и нефункциональных?

Бизнес-требования описывают цели организации и ожидаемый результат проекта. Например, сократить подготовку отчёта с 2–3 дней до 10 минут.

Функциональные требования определяют, какие действия должна выполнять система: загружать данные, рассчитывать KPI, показывать дашборд и формировать отчёты.

Нефункциональные требования описывают характеристики работы системы: производительность, безопасность, надёжность, совместимость и удобство использования.

### 2. Каким критериям должна соответствовать качественная User Story?

Качественная User Story формулируется в виде: «Как роль, я хочу выполнить действие, чтобы получить ценность». Она должна соответствовать критериям INVEST:

- Independent — независимая;
- Negotiable — обсуждаемая;
- Valuable — ценная для пользователя или бизнеса;
- Estimable — поддающаяся оценке;
- Small — достаточно небольшая для выполнения за один спринт;
- Testable — проверяемая с помощью критериев приёмки.

### 3. Зачем нужны критерии приёмки и как они связаны с тестированием?

Критерии приёмки задают условия, при которых User Story считается выполненной. Они уточняют ожидаемое поведение системы и помогают избежать разного понимания требования. На их основе составляются тестовые сценарии. Формат Given–When–Then описывает начальное условие, действие пользователя и ожидаемый результат.

### 4. Какие элементы включает Use Case-диаграмма?

Use Case-диаграмма включает:

- акторов — пользователей или внешние системы;
- варианты использования — действия, выполняемые системой;
- связи коммуникации между акторами и вариантами использования;
- отношения `include`, `extend` и обобщение между вариантами использования;
- границу системы, если необходимо отделить функции системы от внешних участников.

### 5. Что такое backlog и как он приоритизируется?

Product Backlog — это упорядоченный список User Stories, требований и задач продукта. В данной работе используется метод MoSCoW:

- Must have — обязательно для запуска;
- Should have — важно, но не блокирует запуск;
- Could have — желательно;
- Won't have — не входит в текущий релиз.

Дополнительно User Stories оцениваются в Story Points и распределяются по спринтам.

### 6. Как связаны User Stories, Use Cases и backlog?

User Story кратко описывает потребность и ценность функции от лица пользователя. Use Case подробно показывает взаимодействие актора с системой для реализации этой потребности. Backlog объединяет User Stories в упорядоченный план и содержит их приоритеты, оценки, спринты и статусы.

### 7. Какие методы сбора требований вы знаете? В каких ситуациях они применяются?

- Интервью применяют для подробного выяснения целей, проблем и ограничений у конкретных заинтересованных лиц.
- Анкетирование используют для сбора однотипных ответов у большого количества пользователей.
- Наблюдение помогает изучить реальный рабочий процесс и выявить неочевидные действия.
- Анализ документов применяют для изучения существующих отчётов, регламентов и форм данных.
- Воркшоп используют для совместного обсуждения и согласования требований несколькими участниками.
- Прототипирование помогает проверить понимание интерфейса и уточнить ожидания пользователей до разработки.
