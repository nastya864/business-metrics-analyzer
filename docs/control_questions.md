# Ответы на контрольные вопросы

## Практическое занятие № 1

### 1. Чем отличается Git от GitHub?

Git — распределённая система контроля версий, которая хранит историю изменений и работает локально. GitHub — веб-платформа для размещения Git-репозиториев, совместной работы, проверки изменений и Pull Request.

### 2. Для чего используется виртуальное окружение Python?

Виртуальное окружение изолирует зависимости проекта от системного Python и других проектов. Это предотвращает конфликты версий и помогает воспроизводить окружение разработки.

### 3. Что такое commit, branch, remote и Pull Request?

- **Commit** — зафиксированное изменение в истории репозитория.
- **Branch** — отдельная линия разработки.
- **Remote** — связанный удалённый Git-репозиторий.
- **Pull Request** — запрос на проверку и слияние изменений одной ветки в другую.

### 4. Зачем нужен `.gitignore`?

`.gitignore` исключает из контроля версий временные файлы, локальные настройки, виртуальные окружения, секреты и результаты сборки.

### 5. Как организовать командную работу с помощью Git?

Работу выполняют в отдельных тематических ветках. Изменения фиксируют небольшими коммитами, отправляют в удалённый репозиторий и объединяют с `main` через Pull Request после проверки.

### 6. Какие файлы необходимы учебному проекту?

Обычно нужны `README.md`, `.gitignore`, документация в `docs/`, исходный код и файл зависимостей, если проект содержит исполняемое приложение.

### 7. Что произойдёт, если два разработчика изменят один участок файла?

При слиянии может возникнуть конфликт. Разработчик должен вручную выбрать итоговый вариант, удалить маркеры конфликта, проверить результат и завершить слияние коммитом.

## Практическое занятие № 2

### 1. Чем отличаются бизнес-, функциональные и нефункциональные требования?

Бизнес-требования описывают цели организации и ожидаемую ценность. Функциональные требования определяют, что должна делать система. Нефункциональные требования задают характеристики её работы: производительность, безопасность, надёжность и удобство.

### 2. Каким критериям должна соответствовать качественная User Story?

User Story формулируется как «Как роль, я хочу действие, чтобы получить ценность» и проверяется по INVEST: Independent, Negotiable, Valuable, Estimable, Small, Testable.

### 3. Зачем нужны критерии приёмки и как они связаны с тестированием?

Критерии приёмки задают проверяемые условия готовности User Story. На их основе создают тестовые сценарии. Формат Given–When–Then фиксирует начальные условия, действие и ожидаемый результат.

### 4. Какие элементы включает Use Case-диаграмма?

Диаграмма включает акторов, варианты использования, границу системы, связи акторов с вариантами использования и отношения `include`, `extend` или обобщения.

### 5. Что такое backlog и как он приоритизируется?

Product Backlog — упорядоченный список функций и задач продукта. В работе применяется MoSCoW: Must have, Should have, Could have и Won't have. Дополнительно учитываются Story Points и бизнес-ценность.

### 6. Как связаны User Stories, Use Cases и backlog?

User Story кратко описывает пользовательскую потребность. Use Case подробно показывает сценарий взаимодействия с системой. Backlog объединяет User Stories в план с приоритетами, оценками и спринтами.

### 7. Какие методы сбора требований применяются?

- интервью — для подробного выяснения целей и ограничений;
- анкетирование — для сбора однотипных ответов у большой группы;
- наблюдение — для изучения реального процесса;
- анализ документов — для исследования отчётов, форм и регламентов;
- воркшоп — для совместного согласования требований;
- прототипирование — для проверки понимания интерфейса и сценариев.
