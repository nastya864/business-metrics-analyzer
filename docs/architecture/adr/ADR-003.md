# ADR-003. Использование JWT для аутентификации

## Статус

Принято.

## Контекст

В системе предусмотрены роли коммерческого директора, менеджера по продажам, аналитика и администратора. REST API должен проверять личность пользователя и его права на операции с коммерческими данными. В дальнейшем API может использоваться адаптивным или мобильным клиентом.

## Решение

Использовать короткоживущий JWT access token, передаваемый в заголовке `Authorization: Bearer`. Токен содержит идентификатор пользователя и его роль. Пароли хранятся только в виде стойкого хеша. Проверка прав выполняется на стороне REST API для каждого защищённого сценария.

## Альтернативы

1. Серверные сессии — позволяют немедленно отзывать доступ, но требуют общего хранилища сессий при масштабировании приложения.
2. API-ключи — подходят для интеграций между системами, но неудобны для входа пользователей и ролевой модели.
3. OAuth 2.0 через внешнего провайдера — полезен для корпоративного SSO, но избыточен для первого учебного релиза.

## Последствия

Положительные:

- REST API не хранит состояние пользовательской сессии;
- один механизм подходит для Web UI и будущего мобильного клиента;
- роль может проверяться без дополнительного обращения к хранилищу на каждом запросе.

Отрицательные:

- выпущенный токен нельзя мгновенно отозвать без дополнительного списка блокировки;
- необходимо безопасно хранить ключ подписи и настроить срок действия токена;
- изменение роли пользователя применяется после обновления токена.
