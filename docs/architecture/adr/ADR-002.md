# ADR-002. Выбор PostgreSQL для основной базы данных

## Статус

Принято.

## Контекст

Система хранит пользователей, роли, данные о продажах и результаты расчёта KPI. Импорт может содержать до 1 млн записей. Необходимы транзакции, ограничения целостности, выборки по периодам и агрегирование данных для дашборда.

## Решение

Использовать PostgreSQL 16 как основную реляционную СУБД. Доступ к данным реализовать через SQLAlchemy и паттерны Repository и Unit of Work. Для часто используемых фильтров по периоду и организации предусмотреть индексы.

## Альтернативы

1. SQLite — не требует отдельного сервера, но хуже подходит для параллельной записи, облачного развёртывания и большого объёма данных.
2. MongoDB — обеспечивает гибкую схему, однако основные сущности проекта имеют устойчивые связи и требуют транзакционной целостности.
3. Хранение только в CSV/Excel — удобно для обмена, но не обеспечивает конкурентный доступ, связи и эффективные аналитические запросы.

## Последствия

Положительные:

- поддержка ACID-транзакций и ограничений целостности;
- развитые средства агрегирования и индексирования;
- надёжная работа с объёмом до 1 млн записей и выше;
- доступность готового Docker-образа и средств резервного копирования.

Отрицательные:

- требуется отдельный контейнер и администрирование СУБД;
- необходимо управлять миграциями схемы;
- производительность зависит от корректных индексов и запросов.
