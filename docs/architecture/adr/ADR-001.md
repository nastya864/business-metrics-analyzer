# ADR-001. Выбор архитектурного стиля

## Статус

Принято.

## Контекст

Business Metrics Analyzer разрабатывается как учебный MVP командой из 3–4 человек. Система должна поддерживать импорт до 1 млн записей о продажах, расчёт KPI, дашборд, отчёты и разграничение доступа. Требуется быстро получить работоспособную версию, сохранив возможность развития отдельных функциональных областей.

## Решение

Использовать слоистый модульный монолит с элементами Clean Architecture:

- Presentation — Web UI и контроллеры FastAPI;
- Application — сервисы пользовательских сценариев;
- Domain — модели, правила и стратегии расчёта KPI;
- Infrastructure — PostgreSQL, Redis, S3/MinIO, SMTP и внешние интеграции.

Функциональные области аутентификации, импорта, KPI и отчётов разделяются на модули, но развёртываются как одно приложение FastAPI.

## Альтернативы

1. Монолит без разделения на слои — быстрее начать разработку, но бизнес-логика будет связана с FastAPI и SQLAlchemy.
2. Микросервисы — обеспечивают независимое масштабирование, но требуют отдельного развёртывания, мониторинга и сетевого взаимодействия для каждого сервиса.
3. Serverless — удобен при нерегулярной нагрузке, но усложняет длительную пакетную обработку больших файлов.

## Последствия

Положительные:

- единая сборка и простое развёртывание MVP;
- предметная логика тестируется независимо от инфраструктуры;
- модули можно позднее выделить в отдельные сервисы.

Отрицательные:

- все модули масштабируются вместе;
- ошибка процесса приложения может затронуть всю систему;
- границы модулей необходимо контролировать на уровне структуры кода.
