# Архитектура Business Metrics Analyzer

## 1. Обзор системы

Business Metrics Analyzer — веб-приложение для загрузки и проверки данных о продажах, автоматического расчёта KPI, отображения аналитического дашборда и формирования отчётов.

Основные пользователи системы:

- коммерческий директор;
- менеджер по продажам;
- аналитик;
- администратор системы.

В границы системы входят управление пользователями и ролями, импорт данных, расчёт KPI, визуализация результатов, формирование отчётов, настройка метрик и уведомления. Прямая интеграция с учётными системами и отдельное мобильное приложение не входят в первый релиз.

## 2. Архитектурные драйверы

| ID | Драйвер | Тип | Приоритет | Влияние на архитектуру |
|---|---|---|---|---|
| AD-01 | Время отображения дашборда — не более 3 секунд при стандартной нагрузке | Нефункциональный | Высокий | Индексы PostgreSQL, кэширование результатов в Redis, предварительный расчёт часто используемых KPI |
| AD-02 | Обработка до 1 млн записей о продажах | Нефункциональный | Высокий | Пакетный импорт, фоновые задачи, постраничная обработка, хранение данных в PostgreSQL |
| AD-03 | Разграничение доступа к коммерческим данным по ролям | Нефункциональный | Высокий | Аутентификация по JWT, ролевая модель RBAC, HTTPS и аудит значимых действий |
| AD-04 | MVP должен быть подготовлен за 6 недель командой из 3–4 человек | Бизнес | Высокий | Модульный слоистый монолит вместо микросервисной архитектуры |
| AD-05 | Импорт данных из CSV и Excel | Функциональный | Высокий | Отдельный модуль импорта, адаптеры форматов, проверка структуры и содержимого файла |
| AD-06 | Формирование и экспорт отчётов | Функциональный | Средний | Выделенный модуль отчётов, генерация Excel, хранение сформированных файлов в S3/MinIO |
| AD-07 | Возможность добавить уведомления и мобильный интерфейс | Бизнес | Средний | REST API, независимые прикладные модули и стабильные DTO-контракты |
| AD-08 | Развёртывание в облачной инфраструктуре | Ограничение | Высокий | Docker-контейнеры, Nginx, конфигурация через переменные окружения и проверки состояния сервисов |

## 3. Выбранный архитектурный стиль

Для проекта выбран **модульный слоистый монолит с элементами Clean Architecture**.

Основные причины выбора:

- небольшая команда может разрабатывать и развёртывать одно приложение;
- единый репозиторий и процесс сборки ускоряют подготовку MVP;
- разделение на слои изолирует бизнес-логику от FastAPI, PostgreSQL и внешних сервисов;
- модульные границы упрощают тестирование и развитие функциональных областей;
- при росте нагрузки отдельные модули, например импорт или отчёты, можно выделить в самостоятельные сервисы.

### Рассмотренные альтернативы

| Вариант | Причина отказа для текущего этапа |
|---|---|
| Монолит без слоёв | Быстрый старт, но высокая связанность и сложное тестирование бизнес-логики |
| Микросервисы | Избыточная инфраструктура, распределённые транзакции и дополнительные затраты на сопровождение |
| Serverless | Ограничения длительности выполнения и усложнение пакетного импорта больших файлов |

## 5. Слои и компоненты

| Слой | Основные компоненты | Ответственность |
|---|---|---|
| Presentation | Web UI, FastAPI-контроллеры | Приём HTTP-запросов, проверка DTO, формирование ответов |
| Application | AuthService, SalesImportService, KpiService, ReportService, UserService | Выполнение пользовательских сценариев и координация операций |
| Domain | Sale, User, Report, Kpi, стратегии расчёта, бизнес-правила | Независимая предметная логика |
| Infrastructure | Репозитории PostgreSQL, Redis, JWT-провайдер, генератор Excel, S3/MinIO, уведомления | Работа с данными и внешними технологиями |

Зависимости направлены от внешних слоёв к Domain. Предметная логика не должна импортировать FastAPI, SQLAlchemy, Redis или библиотеки генерации отчётов.

### Интерфейсы ключевых компонентов

| Компонент | Интерфейс | Ключевые методы |
|---|---|---|
| `AuthService` | `IAuthService` | `login(credentials) -> TokenDto`, `verify_token(token) -> UserDto` |
| `SalesImportService` | `ISalesImportService` | `import_csv(file) -> ImportResult`, `validate(records) -> ValidationResult` |
| `KpiService` | `IKpiService` | `calculate_period(period) -> KpiResult`, `get_dashboard(period) -> DashboardDto` |
| `ReportService` | `IReportService` | `generate(report_type, period) -> ReportFile`, `export_excel(report_id) -> bytes` |
| `UserService` | `IUserService` | `create_user(data) -> UserDto`, `assign_role(user_id, role) -> UserDto` |

### Функциональные модули

1. **Аутентификация и пользователи** — вход, JWT, роли, управление пользователями.
2. **Импорт продаж** — загрузка CSV/XLSX, валидация, пакетная запись данных.
3. **Расчёт KPI** — выручка, средний чек, конверсия и рентабельность.
4. **Дашборд** — получение агрегированных показателей и визуализация.
5. **Отчёты** — формирование, экспорт и хранение файлов.
6. **Настройка метрик** — управление доступными KPI и пороговыми значениями.
7. **Уведомления** — информирование о критических изменениях показателей.
8. **Аудит** — журналирование входов, импорта данных и административных действий.

## 7. Технологический стек

| Область | Технология |
|---|---|
| Backend API | Python 3.10+, FastAPI, Uvicorn |
| Доступ к данным | SQLAlchemy |
| Основная БД | PostgreSQL 16 |
| Кэш | Redis 7 |
| Обработка данных | pandas |
| Экспорт отчётов | openpyxl |
| Файловое хранилище | S3 или MinIO |
| Reverse proxy | Nginx |
| Развёртывание | Docker, Docker Compose |

### Параметры развёртывания

| Узел | Образ / ПО | Ресурсы | Назначение |
|---|---|---|---|
| Nginx | `nginx:alpine` | 0.5 CPU, 256 MB | Reverse proxy и завершение TLS |
| App | `bma-api:latest` | 1 CPU, 1 GB | REST API и бизнес-логика приложения |
| PostgreSQL | `postgres:16` | 2 CPU, 2 GB | Хранение пользователей, продаж и KPI |
| Redis | `redis:7-alpine` | 0.5 CPU, 512 MB | Кэширование KPI |
| MinIO | `minio/minio` | 0.5 CPU, 512 MB | Хранение сформированных отчётов |

## 8. Ограничения и компромиссы

- Redis и S3/MinIO увеличивают число инфраструктурных компонентов, но улучшают производительность и отделяют файлы отчётов от приложения.
- Единое приложение проще развёртывать, но оно не обеспечивает независимое масштабирование всех модулей.
- Обработка больших файлов должна выполняться в фоне; мгновенный импорт 1 млн записей не гарантируется.
- Точные формулы KPI и стандартная нагрузка должны быть подтверждены заказчиком.
- Уведомления и мобильный интерфейс не блокируют выпуск MVP.

## 9. План развития архитектуры

1. Добавить очередь фоновых задач для импорта и формирования крупных отчётов.
2. Настроить мониторинг, централизованные логи и резервное копирование PostgreSQL.
3. При росте нагрузки выделить модуль импорта или отчётов в отдельный сервис.
4. Добавить интеграцию с учётными системами через адаптеры API.
5. Реализовать адаптивный интерфейс или отдельный мобильный клиент поверх существующего REST API.
